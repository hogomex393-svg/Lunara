**The three things that change once context + tools are turned on:**

1. **Specificity** — the baseline gives generic wellness advice; the default variant references the user's actual cycle day, recent symptoms, and dates.
2. **Tool usage on pattern questions** — every case in the `pattern_detection` category triggers `get_recent_symptoms`. The baseline cannot answer these without making things up.
3. **Token cost ~2.2×** — the price of grounding. Mostly spent in tool result messages (recent logs serialised as JSON). For an internal app this is acceptable; for a free-tier consumer launch we'd want to trim the log payload.

## What I learned from running this

1. **Tool gating in templates works.** The `luna_data_analyst` template (not shown above; included in the full run) is the strictest — it *always* calls `get_recent_symptoms` before answering. The default variant only calls it when the question is data-shaped. This is exactly the behaviour I want: ground when it matters, stay light otherwise.

2. **The "half-agent" context injection earns its keep.** ~40% of cases that *could* call `get_cycle_phase` skip the call because the cycle day is already in the system prompt. That saves a round trip.

3. **Token cost is a real lever.** The biggest cost is `get_recent_symptoms` returning the full JSON of 14 days of logs. Next iteration would have the tool pre-summarise (top symptoms, counts) instead of returning raw records.

4. **The baseline isn't useless.** For pure emotional cases (`cramp_basic`, `anxious_pms`, `sleep_period`) the baseline answers are roughly as good as the grounded ones, at 30% of the cost. A production setup might route emotional queries to a cheaper, context-light template and data queries to the expensive grounded one.
